# Phase 4E — generation proof-of-concept recovery

Research checked **18 October 2026**. This phase made one additive TypeScript contract and this report. No generation was submitted, no Space was created, and no production endpoint, migration, RLS policy, administrator role, or billing setting was changed. The earlier Phase 4D work and its recorded failed request remain intact.

## Phase 4D failure: what is known

**Confirmed:** the authorized synthetic request to `zai-org/CogVideoX-2B-Space` returned a Gradio `event: error` with `data: null`; it returned no output path or video. The app UI and published source bound the Generate button to three inputs (`prompt`, steps, guidance), while the callback signature requires a fourth `model_choice` argument. The source therefore contains an apparent input/signature mismatch. The actual hosted exception and whether the callback reached model inference are not observable from the response; owner runtime logs were unavailable.

**Conclusion:** the experiment failed and produced no evidence of inference. The callback mismatch is a plausible explanation, not a confirmed runtime cause. This report evaluates other demos and does not retry that Space. The earlier anonymous request may have consumed some quota; the public API does not expose the amount, so remaining quota is unknown.

### Recommended next test

Recommend **one public synthetic text-to-video call to Lightricks LTX Video Fast**, with no image upload, no Vidio project data, prompt enhancement disabled, target duration 2 seconds, default 512×704, 30fps, and fixed seed 42. The app randomizes seeds by default; a reproducible call should explicitly set “Randomize Seed” off. The output is expected around 57 frames / 1.9 seconds because the code rounds frames to the model's `8n+1` pattern. The model callback cap is 60 seconds and the function is xlarge, so budget **at most 120 GPU-quota seconds** for one call; queue wait, model cold start, actual successful runtime, and quota consumed are unverified. A signed-in Free allowance of 300 quota seconds would leave 180 seconds if the entire 120-second maximum is charged; unauthenticated quota is only 120 seconds, leaving no slack. **Do not call until approval and, ideally, confirm remaining account quota is at least 120 seconds.** ZeroGPU time limits can terminate the run; there is no model-specific public runtime benchmark to promise success. No billing should be enabled.

This is a proof-of-concept candidate, not a production model selection. The custom LTX terms require a separate commercial review before product use. If those terms do not fit the planned use, the Apache Wan2.1 1.3B model remains attractive technically (official report: 8.19 GB and about four minutes for a 5-second 480p video on RTX 4090), but the public model card alone does not establish a compatible, reliable ZeroGPU Space. Do not infer that the prior failed CogVideoX Space can be reused.

## React architecture and local code

The current React application is a client-side Vite app with Supabase authentication/cloud repository support and local-storage fallback for projects. Project records currently contain title, brief, format, and timestamps. Inspiration references live separately in `src/data/inspirationVideos.ts`; they are curated media and must remain distinct from generated output.

Added `src/generation/contracts.ts` as a provider-independent, type-only boundary for a future authenticated application backend. It describes requests, server-owned jobs, truthful terminal states, and generated MP4 metadata with an opaque artifact ID, not a provider URL. It has no concrete provider, fake progress, mock result, database mapping, or user interface. A later browser adapter must talk only to the authenticated Vidio API; provider tokens remain server-side. Keep generated outputs in a separate owned artifact collection/repository rather than inserting them into inspiration references.

## Smallest remaining platform prerequisites

1. **Authenticated request:** choose the server runtime; define bounded request/response schema; verify Supabase JWT server-side; derive `owner_id` from the verified subject; confirm project access under that caller; accept an idempotency key. Never accept a client-supplied owner or provider URL.
2. **Per-user jobs and ownership:** after a separately reviewed migration, create job metadata with owner/project foreign keys and explicit state constraints. Add owner-only RLS for reads and server-side checks for create/cancel/retry/delete/download. Test two accounts can each see their own jobs/artifacts and cannot enumerate or retrieve the other's.
3. **Limits and safety:** enforce server-side prompt length, allowlisted model/revision, duration/frame/resolution/step caps, global concurrency, per-user active/queued limits, rate limits, storage budget, and atomic quota reservation. Define the content policy, abuse handling, reporting/deletion path, and provider/moderation behavior before multi-user access.
4. **Private output storage:** create a private bucket only after policy review. Use server-generated owner/job paths, validate the completed MP4, record dimensions/duration/bytes/checksum/model revision/seed, and serve via owner-checked short-lived download or Range-capable server stream. Retention/deletion must remove both object and metadata.
5. **Failure recovery:** implement lease/heartbeat and `queued → running → succeeded | failed | cancelled`; detect stale leases and mark interrupted work failed. Bound retry count and make retry idempotent. Cancellation should signal the worker and reconcile reserved quota. Never mark succeeded before validating an artifact.
6. **Secure admin (separate plan):** define a minimal platform-operations permission set. Use server-managed role data or trusted `app_metadata` and signed claims; never user-editable `user_metadata`. Enforce the role on every privileged server action, add MFA and immutable audit records, test claim removal/revocation and privilege escalation denial. Admin job-health/quota controls must not grant broad access to user projects or artifacts. No administrator permission is granted now.

The existing secure worker and administrator plans remain in [AI_GENERATION_PLAN.md](AI_GENERATION_PLAN.md) and [PHASE_4D_REPORT.md](PHASE_4D_REPORT.md). Two-account RLS isolation remains pending. No RLS was weakened and no migration was created.
