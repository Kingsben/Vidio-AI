# Phase 4D — first real video generation proof of concept

Research checked **18 October 2026** against the official sources linked below. This phase made documentation changes only. After the user authorized one synthetic prompt to an existing public Space, one inference request was submitted. The request failed before returning a video; no generated artifact was received. No Space was created and no production endpoint, database migration, or application integration was added.

## Candidate and free-compute decision

The preferred small text-to-video candidate remains **Wan-AI/Wan2.1-T2V-1.3B**. Its exact checkpoint is listed as **Apache License 2.0** on its Hugging Face model card. Apache 2.0 permits commercial use subject to its conditions, including preservation of notices; it does not grant rights to input material or third-party likenesses. Wan's official instructions say this checkpoint supports 480p, recommend 480p for stability, require PyTorch 2.4 or newer for the repository path, and document CPU offload/T5-on-CPU flags. The Diffusers model card documents `diffusers`, `transformers`, and `accelerate` and a CUDA pipeline example. The official benchmark is **five seconds at 480p in about four minutes on an RTX 4090**, with **8.19 GB VRAM** reported. That is a reference, not a prediction for ZeroGPU. Sources: [model card](https://huggingface.co/Wan-AI/Wan2.1-T2V-1.3B), [official Wan2.1 inference instructions](https://github.com/Wan-Video/Wan2.1#run-text-to-video-generation), [official ZeroGPU documentation](https://huggingface.co/docs/hub/spaces-zerogpu).

For an already-hosted endpoint, **CogVideoX-2B** was also evaluated. The exact 2B checkpoint is Apache 2.0, and its official model card documents Diffusers, Transformers, and Accelerate. Official CogVideoX materials report about 4 GB VRAM for optimized Diffusers FP16 and about 90 seconds for a 49-frame/6-second, 50-step video on an A100. The 4 GB figure was tested on A100/H100, not arbitrary GPUs. The official `zai-org/CogVideoX-2B-Space` was live on ZeroGPU and advertises 49-frame text-to-video, default 50 inference steps, and a 240-second ZeroGPU function duration. Its UI states the demonstration is for academic research and experiential use. Model and demo sources: [2B model card](https://huggingface.co/zai-org/CogVideoX-2b), [2B model licence](https://huggingface.co/zai-org/CogVideoX-2b/blob/main/LICENSE), [official model performance table](https://github.com/THUDM/CogVideo), [Space source](https://huggingface.co/spaces/zai-org/CogVideoX-2B-Space/blob/main/app.py).

Hugging Face currently documents ZeroGPU `large` as half of an NVIDIA RTX Pro 6000 Blackwell with 48 GB VRAM. It supports Gradio Spaces and PyTorch-based workloads; the published compatibility table includes PyTorch 2.8 through current supported releases and Python 3.10.13 or 3.12.12. The documented 48 GB slice exceeds Wan's published footprint. Wan therefore appears **hardware-feasible in principle** on the standard ZeroGPU slice, but no official source guarantees this exact Space/model/dependency combination or its cold-start memory and runtime. The first run should use one short prompt, 480p, one seed, no prompt expansion, and 17 frames (the usual 16n+1 frame pattern, about one second at 16 fps) if the selected pipeline accepts that frame count. If it rejects that frame count, stop and record the actual minimum; do not claim a 1–2 second result.

The current documented allowance is **five GPU-minutes per Free account per 24 hours after first use**, with medium queue priority. Unauthenticated use has a **two-minute** allowance and low priority. A standard free account may host up to two ZeroGPU Spaces only when the account is in good standing, its email is verified, and the account is older than 30 days. Those conditions are account-specific. This environment has no Hugging Face CLI installation/login available, and the account's verification, age, quota balance, and standing have not been checked. No eligible account has therefore been established. Do not add credits: Hugging Face documents paid over-quota credits for certain tiers, and this experiment has a strict $0 boundary.

The technically plausible proposal was not sufficient on its own, so after the user's authorization one synthetic prompt was sent to the existing public `zai-org/CogVideoX-2B-Space` endpoint. The exact prompt was: “A tiny paper boat drifts across a quiet puddle as raindrops form ripples; fixed overhead camera, soft morning light, gentle motion, simple composition.” The call used five inference steps and guidance 3.5; no image was sent and the optional prompt-enhancement endpoint was not called. The public API returned event ID `a5260b6ecf6e42289e0bbfcaa041f033`. Polling its documented Gradio call route returned only `event: error` / `data: null`; there was no output path or video to inspect.

The exact cause was not exposed by the public API. Inspection of the Space's currently published `app.py` identifies a likely cause: `generate(prompt, num_inference_steps, guidance_scale, model_choice, progress=...)` requires a fourth `model_choice` argument, while the button binding supplies only `[prompt, num_inference_steps, guidance_scale]`. That explains the failure before a result, but without owner logs it cannot be confirmed as the runtime exception. The Space's configuration showed the live endpoint binding has those same three inputs. The attempt therefore produced **no evidence of real model inference** and **no first generated video**. No retry was made, preserving the one-request authorization.

The public route is available without credentials on the Space page, but remaining anonymous quota is not exposed by its API. Hugging Face documents a two-minute daily allowance for unauthenticated ZeroGPU requests and five minutes for an eligible signed-in free account. We used no Hugging Face token, so we did not verify account-specific eligibility or remaining quota; exact quota consumed by the failed request is unknown. No paid service, credit balance, or billing setting was used.

The local Intel UHD Graphics 620 / 7.38 GiB RAM machine remains unsuitable for assuming CUDA support. No local model was installed and no large weights were downloaded.

## Reproducible proof requirements

After explicit authorization for the chosen hosting and data-transfer route, create an isolated experiment outside the application repository (or in a temporary review directory) with a minimal Gradio interface, pinned model revision, dependency lock, and an allowlisted harmless prompt authored for this benchmark. Keep source code and artifacts private where the selected account permits; avoid any existing Vidio project brief, user content, image, credential, or personal data. Do not enable sharing, public API access, or paid credits.

Before submitting, inspect the Space visibility, source visibility, API exposure, and quota behavior. Configure the GPU function to a bounded duration and one request at a time. If the only usable route is a public Space, explain that anyone can invoke it and see its code/output route before proceeding. Stop before generation if visibility, billing, or account quota cannot be confirmed as $0 and appropriately restricted.

Count success only when all of the following evidence is recorded: exact model revision and licence; actual GPU allocation; generated frame count and output dimensions; seed and inference settings; wall time and GPU quota consumed; model and dependency versions; an artifact created by that inference call; and a successful local decode/frame inspection proving it is a valid video. Keep the original artifact and a SHA-256 digest. A queued request, downloaded demo, stock clip, prerecorded sample, static image, or mocked progress is not proof.

## Later authenticated application integration

Keep the generation worker behind a server-side API. The browser sends its Supabase access token and a project ID plus bounded prompt/settings; it never receives a provider token, model credential, service-role key, or arbitrary model URL. The API validates the JWT with Supabase Auth, derives the caller ID from the verified subject, and checks project access through the caller's normal authenticated/RLS-constrained client. It ignores any client-supplied owner ID.

Use an atomic job record and quota reservation with an idempotency key. Apply per-user queue limits, a global worker concurrency cap, prompt/frame/resolution/time/output caps, and rate limits on the server. A worker claims jobs with a lease and heartbeat, supports cancellation, and records only real worker events. Expired jobs become failed/interrupted; retries are bounded and idempotent. Reserve quotas before compute and release or reconcile them on cancellation/failure.

Write artifacts to private object storage under server-generated owner/job paths. Store owner ID, project ID, model revision, seed, settings, status, byte size, checksum, and retention timestamp. Enforce owner checks at every status, cancel, download, delete, and retry operation. Use short-lived authorized downloads or a server stream with Range support. Never construct an object path from unchecked user input. Apply retention and deletion to both database metadata and object storage.

Keep admin and ordinary access separate. Users can read, cancel, and delete only their own generation jobs and artifacts. Enforce that rule in server authorization and storage/database policies; a hidden UI control is not a security boundary. Audit privileged operations and do not log prompts or tokens by default. Add two-account positive/negative isolation tests before multiuser release.

Content safety should start with bounded prompt validation and an explicit use policy, then use provider/model safety controls where available and manual review for an owner-only experiment. Before wider use, add reporting, deletion, abuse-rate controls, and a documented response path. Do not present simple keyword matching as complete moderation. Handle provider queue failures, OOM, model-load errors, timeout, malformed or oversized MP4, cancellation races, storage failure, and duplicate requests with truthful states and no success until a validated artifact exists.

## Separate future administrator architecture

No administrator role was granted and no migration or policy was changed. For a later implementation, use a server-managed role source (for example, a narrowly writable role table readable by a Supabase Custom Access Token Hook, or trusted `app_metadata`) and derive a short authorization claim in the signed JWT. Never use user-editable `user_metadata` for authorization. Verify the token and role on every privileged server endpoint; role-dependent frontend navigation is only presentation. Supabase documents both server-enforced custom-claim RBAC/RLS and that service-role/secret keys bypass RLS and must remain server-side.

Give the administrator a small permission set for platform operations such as inspecting aggregate job health, retrying or cancelling stuck jobs, managing global quotas, disabling a model, and handling reports. Keep ordinary project and generated-artifact access owner-scoped. If exceptional content access is ever justified, require a separate permission, documented case reason, short time-bound grant, strong MFA, and immutable audit entry; do not create a general admin bypass for user projects. Prefer a separately authorized support workflow that reveals the minimum required data.

Before assigning any admin role: define permissions and threat model; create/review migrations and RLS policies; ensure end users cannot self-assign; verify custom JWT claim issue, refresh, removal/revocation, and stale-token behavior; implement server checks and audit; test denied escalation and allowed operations; and finish the pending two-account project/job/storage isolation tests. Existing users must continue to access only their own projects. Supabase's guidance recommends RLS as the database boundary and warns that `user_metadata` is user-editable; see [Custom Claims and RBAC](https://supabase.com/docs/guides/api/custom-claims-and-role-based-access-control-rbac), [Row Level Security](https://supabase.com/docs/guides/database/postgres/row-level-security), and [API keys](https://supabase.com/docs/guides/getting-started/api-keys).
